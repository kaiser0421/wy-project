## Challenges

**C1. Keep the in-transaction counter and `synchronous_commit=on`.** With a measured **1–2 ms total lock hold**, the ceiling is **500–1,000 state-changing transactions/s per event**. If 1–2 ms is the WAL flush alone, the ceiling is lower. The 3,000 VUs also generate conflicts, sold-out responses, and idempotent retries, which should bypass the counter. Measure successful mutations/s and p95/p99 counter wait during the opening burst. Batch independent expirations and keep the counter update and outbox insert immediately before commit. Async commit can lose an acknowledged hold and reuse a sequence already published to Redis. `commit_delay` cannot group commits from transactions still waiting on that same row. I’d revisit CDC if the measured counter wait dominates the burst. SQL polling with `pg_logical_slot_get_changes` advances consumption before Redis publication is safe. A correct CDC design needs controlled acknowledgments, deduplication, WAL retention monitoring, and a coordinated snapshot cursor. [PostgreSQL WAL settings](https://www.postgresql.org/docs/16/runtime-config-wal.html), [logical decoding functions](https://www.postgresql.org/docs/16/functions-admin.html)

**C2. Concede the fixed four-frame/500 ms cutoff. Use the shared ring.** Keep 50 ticks at 100 ms, with byte limits and one in-flight frame per connection. At 1,000 changes/s × 40 B, five seconds is roughly **200 KB of encoded changes per event per process**, before indexing and object overhead. Store a cursor per connection and reuse encoded frames or shared coalesced ranges. The range must be contiguous and carry the final state of every seat touched. A fixed 512-seat threshold could force healthy clients to resync after just 0.5 s of distinct changes. If a client falls outside the ring, close the stream and replay from Redis. A blocked socket may never deliver a `resync` event. On a replay gap, use a per-process, single-flight cached PostgreSQL snapshot, refreshed at most once per second, and bridge from its `seq + 1` before joining live. If the bridge is missing, invalidate the cache and retry with jitter. At 40 KB each, 2,000 snapshots still cost **80 MB** of egress even with shared generation.

**C3. Concede a custom spool. Keep a persistent file as the batch writer’s input.** A RAM queue can lose one batch in flight **plus** everything queued. With a full 50,000-record queue at 5,000/s, that is about **10 seconds** of arrivals, and a dead worker cannot report its exact losses. Use mounted nginx and service log files, tail into `COPY` batches, and advance file offsets only after commit. Deduplicate replay by file identity and offset, and retain rotated files until consumed. This survives an API `kill -9` for records already written and reuses the same collector as C5. Keep the partitioned outbox as the seat-event archive with retention independent of Redis. [nginx access logging](https://nginx.org/en/docs/http/ngx_http_log_module.html)

**C4. Concede the OTel SDK and exporter.** The required lookup is a PostgreSQL query on `request_id`. Have nginx set the trusted ID, propagate it through HTTP, jobs and outbox records, and carry the originating ID into payment callbacks. Use `contextvars` and structured logs with service, operation ID, parent operation ID, and local sequence. If you emit `traceparent`, validate it and propagate parent IDs per hop. Use timestamps for display and causal links for cross-service ordering. A request-wide sequence would itself need coordination across concurrent services. [W3C Trace Context](https://www.w3.org/TR/trace-context/)

**C5. Pick (b) for live edge charts and ASGI for attribution.** Tail nginx JSON containing `$request_id`, `$status`, `$request_time`, and `$msec`. At 5,000 completions/s × 250 B, the input is about **1.25 MB/s**. Aggregate short-request completions into one-second RPS, 5xx and latency histograms. Count active SSE streams from worker gauges and chart stream opens separately. Nginx sees gateway failures that ASGI never receives. Compare matched routes and statuses for divergence, with collector-lag and completeness indicators so a stuck tail cannot look like zero traffic. [nginx access logging](https://nginx.org/en/docs/http/ngx_http_log_module.html)

## Failure scenarios

**F1. API dies mid-fan-out.** Clients that applied `501..520` resume at `520`. Clients that received only a partial SSE frame resume at `500` and replay the range. Use the application’s last successfully applied cursor on reconnect, including after a handler failure. Native `Last-Event-ID` tracks EventSource delivery. The replacement worker validates contiguous coverage, bridges replay into live delivery, and falls back to a snapshot on a gap. The affected clients briefly show stale or reconnecting. The other replicas keep serving. [HTML SSE standard](https://html.spec.whatwg.org/multipage/server-sent-events.html)

**F2. Redis restarts empty.** A reader blocked at `900` cannot detect the reset from `XREAD` alone. Use a Redis generation marker and generation-scoped stream keys. A missing or changed marker invalidates reader cursors and rings. The relay rebuilds the retained PostgreSQL tail with the **original** IDs, catches up, and marks the generation ready. Clients reconnect with their original DB sequence. Replay `901` onward if coverage exists, otherwise snapshot. The DB publication checkpoint can be ahead of an empty Redis instance, so rebuild from retained outbox rows. [Redis `XREAD`](https://redis.io/docs/latest/commands/xread/), [Redis `XADD`](https://redis.io/docs/latest/commands/xadd/)

**F3. Relay dies after `XADD 777-0`.** The successor acquires the advisory lock and reads checkpoint `776`. In the same generation, it fetches exact ID `777-0` and verifies it against the outbox row. On a match it checkpoints `777` and proceeds to `778`. If absent and the stream ends at `776`, append `777-0`. If the generation changed, or the stream reached `777` and the entry is missing or mismatched, rebuild. Clients that already applied `777` keep it.

**F4. A worker clock is 20 s slow.** Monotonic durations and flush cadence stay correct. Collector receipt time assigns buckets, and retries deduplicate by `(boot_uuid, flush_no)`. Wall-clock log timestamps can invert across services, so retain causal links and local sequence. Set hold deadlines in PostgreSQL and check expiry against a DB clock sample taken after acquiring the relevant locks. SSE uses sequence lag and client monotonic time since the last valid progress heartbeat. Recheck on tab resume. [PostgreSQL clock functions](https://www.postgresql.org/docs/16/functions-datetime.html)

**F5. PostgreSQL is unavailable for 10 s.** DB-dependent requests fail fast with `503`. If commit outcome is unknown, retry with the same idempotency key. Payment callbacks retry and expiry work resumes after recovery. The live collector can still show edge errors and latency if it runs independently of PostgreSQL. DB-backed charts show delayed data or gaps while writes stall. Spool edge logs and buffer metric batches within a fixed budget. Preserve edge completion times and flag delayed receipt-time contributions. Fire a DB-probe alert through the independent monitor, then persist its transition after recovery. SSE can drain already published deltas, but cannot certify freshness. Mark clients stale within five seconds of the last valid progress signal while the tab is active. On restart or failover preserving acknowledged commits, the relay resumes and clients become current after catch-up. If an asynchronous promotion lost commits, fence the old primary, change the feed generation, force fresh snapshots, and reconcile affected orders and payments.
