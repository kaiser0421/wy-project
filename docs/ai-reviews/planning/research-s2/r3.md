Keep SSE, PostgreSQL sequencing, Redis replay, and the shared ring. The two biggest review blockers are a Redis rollback that can silently strand clients and a monitoring chart that can show healthy traffic while data is missing.

## 1. Top five remaining risks

1. **Redis can lose data without losing `stream:gen`.** A restart or failover can preserve the generation and ready flag while losing acknowledged entries. A PostgreSQL checkpoint can then sit ahead of Redis indefinitely. Reconcile Redis against PostgreSQL at takeover and periodically, including missing keys, regressed tails, and holes. Advance checkpoints only through a verified contiguous prefix. An `XADD` ID error alone proves neither presence nor payload equality. On mismatch, rebuild under a fresh generation, fence stale publishers on append, and publish readiness only when the rebuilt range is usable. [Redis XADD](https://redis.io/docs/latest/commands/xadd/), [Redis durability](https://redis.io/docs/latest/commands/waitaof/)

2. **The SSE freshness claim is too strong.** A progress frame sourced from a worker’s cursor or Redis tail can look healthy while the relay is stalled. Use a periodically sampled PostgreSQL head shared across subscribers, and expire the sample itself. Add a deadline to blocked writes and cap concurrent replay and snapshot work. A frozen map can be wrong on every seat for the duration of an outage. Five seconds is a warning threshold while the browser runs, and 110–150 ms is a hypothesis. Poll fallback alone can add 200 ms.

3. **Revocation falls short of immediate invalidation.** Pub/Sub can miss a revoke, leaving an open stream authorized until the next 30-second check. Check authoritative session state on each new admission, including ticket redemption. If revocation must also stop future emissions on existing streams immediately, enforce an authoritative delivery gate and define the boundary for bytes already sent. Bind tickets to session and event, redeem atomically, renew on reconnect, and omit query strings from access logs. [Redis Pub/Sub](https://redis.io/docs/latest/develop/interact/pubsub/)

4. **The checkout transaction contradicts its own ordering.** The counter update precedes the outbox insert and any explicit `NOTIFY`. Define the counter allocation and outbox append as the final database operation, after seat mutations, and cover hold, pay, cancel, expiry, and every other streamed mutation. Keep the counter initially and measure lock-wait and purchase p99 under A. I’d start with polling and add `NOTIFY` if measured latency warrants it. A full notification queue can fail purchase commits. [PostgreSQL NOTIFY](https://www.postgresql.org/docs/current/sql-notify.html)

5. **Telemetry deduplication leaves loss paths open.** Commit the dedup key and metric contribution together, then acknowledge Redis and reclaim pending entries on restart. Freeze the receipt bucket at first durable ingestion. Worker death before flush and Redis loss or trimming can still drop intervals. Track flush gaps, missing workers, and backlog explicitly, and show incomplete windows. The Redis heartbeat is independent of the collector process but shares Redis and the admin delivery path. Monitor that path externally if alerting must survive its failure. [Redis XACK](https://redis.io/docs/latest/commands/xack/)

## 2. Docker-volume log tailing

**Yes, with rename-and-reopen and a defined loss budget.** Rename each segment to a unique durable name and send nginx’s master `USR1` from a process that can signal it. Drain the old descriptor and rediscover rotated files after restart. Avoid `copytruncate`, which can lose writes and reuse offsets. Use device/inode to track an open file, a persistent segment ID for dedup, and checkpoint only complete lines in the same transaction as their inserts. Retain uncheckpointed segments until the disk budget forces eviction, then record the loss. Give each writer its own files or a single rotation owner. For time-partitioned logs, include the partition key in the unique constraint or keep dedup in a separate ledger. [nginx rotation](https://nginx.org/en/docs/control.html), [PostgreSQL partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html)

## 3. Outbox partitioning and retention

Start unpartitioned with `PRIMARY KEY (event_id, seq)`. Hash partitioning by `event_id` preserves uniqueness if scale warrants it. Monthly `recorded_at` partitioning cannot enforce that key as written. Set an explicit archive lifetime after event end, then purge in batches once the event is terminal, all events are published, and rebuild no longer needs the rows. Keep the last 20,000 rows for every event eligible for Redis rebuild, plus all unpublished rows. Section 6.4 explicitly asks for batched database writes of seat events. Batch seat changes within the business transaction and document the batching unit. If the reviewer requires cross-transaction batches, add a batched archive sink and retain the transactional outbox. [PostgreSQL partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html)

## 4. Worker topology

Use **one worker per replica**, starting with three and comparing against six at matched CPU budgets and total DB pool size. Six single-worker replicas have the same six hot-event readers as three two-worker replicas. The gains are per-process balancing and smaller restart blast radius. `least_conn` sees upstream endpoints, so 333 streams per worker is an average, not an allocation. Verify endpoint rediscovery after recreation and measure the busiest worker’s RSS, loop lag, and reconnect load. [nginx upstream balancing](https://nginx.org/en/docs/http/ngx_http_upstream_module.html)

## 5. What fails Q4 and Q6

- **Q4:** PostgreSQL orders committed per-event changes, Redis preserves that order, and each API worker verifies continuity before fan-out. Specify how snapshot, replay and live handoff share a cursor, validate replay across trimming, and advance `Last-Event-ID` only after apply. Version the seat-index layout and force a fresh snapshot on incompatible layout or an unbridgeable cursor. Close slow clients on timeout and explain that coalescing discards intermediate transitions. `requirement.txt` asks for **actual** Scenario B results. Report 2,000 concurrently open streams, commit-to-apply p50/p95/p99, convergence and resync counts under slow readers and Redis recovery. Relay-to-receive omits upstream delay, and writer-response subtraction can go negative.

- **Q6:** Define edge RPS as **completed requests per second**, publish error rates with denominators, and label the latency population. Sample nginx active client sockets separately from open SSE subscriptions because HTTP/2 multiplexes them. Retain counts and histogram buckets, add underflow/overflow, and recompute minute percentiles from merged buckets. A 20-second replica clock error leaves receipt-time placement intact when delivery is timely. Delayed flushes can still pile into one second, and receipt minus producer wall time also contains transport delay. Compare edge and app only for matched routes, attempts and windows. Trust edge for client-facing HTTP outcomes, app for attribution, and PostgreSQL for order and seat truth. Demonstrate HTTP 200s with failing holds while **eligible** inventory remains, detected by the business outcome counter or purchase canary. [nginx access logs](https://nginx.org/en/docs/http/ngx_http_log_module.html), [nginx connection counters](https://nginx.org/en/docs/http/ngx_http_stub_status_module.html)

My remaining disagreements are the generation-only reset trigger, `XADD` errors as dedup proof, the claimed freshness bound, best-effort revocation as immediate invalidation, receipt-time dedup as loss protection, and six workers as the default before measurement.
