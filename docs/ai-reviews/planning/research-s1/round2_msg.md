Sweeper uses the same predicate with clock_timestamp(). Explicit branch "pending_payment but past deadline" => expire+release+record capture+enqueue refund in the callback txn itself.
A2. Callback dedupe insert + state transition + outbox in ONE txn; 2xx only after commit. Event id inside signed body; mockpay re-signs each retry with fresh timestamp.
A3. Separate payment_attempts / payment_captures (unique provider_capture_id) / refunds (stable provider refund key). One accepted capture per order (partial unique). Any other capture -> refund.
A4. Drop the detached 4xx-idempotency write. Only committed success (2xx) is stored; 409/422 business failures are not stored and re-execute on retry (no side effects happened). Advisory try-lock key namespaced; row (user_id,key) is identity; auth before replay; replay includes Location.

## CHALLENGES — please respond to each
C1. Sweeper lock order / one-order-per-txn. Booking: quota row -> seats (NOWAIT / SKIP LOCKED: never waits on seats) -> new private rows. Booking NEVER locks an existing order. Callback/cancel/sweeper: order -> seats -> quota. I claim no cycle exists because quota holders (booking) never wait for order or seat locks (they only wait on their own quota row, which is the first lock). So "order -> quota" is safe and I can keep batched sweeps (claim 200 orders with FOR UPDATE SKIP LOCKED) as long as within the batch I lock quota rows in sorted (user_id,event_id) order via `SELECT ... FROM user_event_quota WHERE (user_id,event_id) IN (...) ORDER BY user_id, event_id FOR UPDATE` before the decrement. Two sweepers claim disjoint orders; their quota sets may overlap but both lock in the same sorted order -> no deadlock. Is there a cycle I am missing (e.g., cancel by same user while that user's booking holds quota and ... ?). Note cancel locks order then quota; booking holds quota and never waits on order. Where's the hole?
C2. Event gate advisory lock on every booking: I think a shared advisory lock taken by ~1-2k txn/s on the same key is lock-manager overhead (no fast path for advisory locks, single lock partition) and adds a new hotspot. Counter-proposal: after publish, booking inputs are FROZEN (zones, prices, sales_start_at; sales_end_at may only be changed by Admin and only... or also frozen). Unpublish is not supported. Delete vs first order is handled by the orders.event_id FK RESTRICT (delete blocks/fails vs. concurrent insert). Sales-window check uses clock_timestamp() inside the txn at allocation time. Is anything still racy? 
C3. Payment attempt creation. Instead of outbox+202, I propose: POST /orders/{id}/payments: txn1 (lock order, require pending & not past deadline, upsert the single non-terminal attempt row with merchant_payment_id = attempt uuid, status 'creating') commit; call mockpay POST /intents with merchant_payment_id as provider idempotency key (provider returns same intent on repeat); txn2 store provider_intent_id, status 'awaiting_customer', store idempotency response; return 201. Kill -9 between: client retry (same key or a new key) finds the existing 'creating' attempt and re-calls create (idempotent) -> converges; reconciler also completes 'creating' attempts older than 30s by re-calling create or marking abandoned when order expired. Synchronous UX, no worker hop. Is that sound?
C4. Outbox ordering. Per-event counter row incremented in every booking txn serializes the hot event's commits (exactly the hotspot I avoid). My counter-proposal: relay does NOT use an id cursor; it polls `WHERE published_at IS NULL ORDER BY id FOR UPDATE SKIP LOCKED`, so a late-committing lower id is still picked up (no loss). A single relay leader per event-partition (advisory lock on hash(event_id) % N) assigns a contiguous per-event stream seq at publish time and XADDs to Redis stream; clients detect gaps via the contiguous publish-seq; each seat delta carries seat.version so clients apply only if newer -> cross-seat reordering is harmless because seats are independent. Snapshot endpoint returns seat map + last published seq (read from relay's durable `event_stream_state(event_id, last_seq)` updated in the same txn that marks published). Hole?
C5. Redis zone sold-out hint: I agree it must not be the authority. But under 3000 VUs after sell-out, nearly all traffic is "zone X sold out" — I'd like a cheap reject. Proposal: in-process per-replica cache of zone available counts read from PG every 250 ms; if 0 -> 409 insufficient-seats with `Retry-After`. Worst case a seat freed by expiry is invisible for ≤ refresh + stall; a stall watchdog disables the hint if age > 2s. It's an admission/availability tradeoff, not an oversell risk. Acceptable if documented?
C6. Pagination. Public listing only shows published events whose sort keys (sales_start_at, created_at, title?) are frozen after publish; cursor = (sort_key, id) keyset bound to filter+sort hash; default sort created_at DESC,id DESC. Remaining holes: (a) late-committing insert with id/created_at behind cursor (created_at = txn start, so commit lag can place it behind an already-passed cursor). Fix: sort by `published_at` set via clock_timestamp at publish commit? Still not commit order. Is a snapshot-materialized cursor worth it, or is documenting "sort by publish sequence assigned by a sequence at publish" enough? What do you recommend that's practical?
C7. Failure ordering for Q1 — give me the single most likely double-sale ordering for MY design (NOWAIT lock + guarded UPDATE + partial unique on active order_items + sweeper + callback), step by step, and whether the design stops it. Also: sweeper expires order O at T, releases seat S; at T+1ms callback for O (success) arrives, sees expired -> refund. Meanwhile S resold to O2. Any ordering where O's late callback marks S sold for O?
C8. Clock seam: I plan an SQL function `app_now()` = clock_timestamp() + coalesce(current_setting('app.clock_offset', true),'0')::interval, used by booking (expires_at), sweeper, callback decision. Prod never sets the GUC. Tests set it per-session (SET LOCAL in the test's sweeper/callback call) or per-role (ALTER ROLE test_app SET ...). Is a GUC seam in prod code acceptable or a liability (e.g., someone setting it via pgbouncer/connection options)? Alternative?
