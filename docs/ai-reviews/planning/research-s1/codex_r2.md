**C1. Keep batched sweeps.** I retract the one-order-per-transaction requirement for the lock graph you described. Claim orders with `SKIP LOCKED`, finish acquiring seat locks, then lock **all** affected quota rows in one `ORDER BY user_id, event_id FOR UPDATE` query on immutable keys before decrementing. Two batches acquire overlapping quota rows in the same order. A single-order cancel holding quota has finished acquiring locks, and a booking holding quota skips or fails on a locked seat. That rules out the proposed cycle among those paths. The proof also requires that no later write waits on a lock outside that graph. The event FK in C2 is one such edge. [PostgreSQL locking clauses](https://www.postgresql.org/docs/16/sql-select.html)

**C2. Freeze both sales bounds and drop the per-booking advisory gate.** Keep two lifecycle edges explicit.

- **Publish vs. import.** Import reads `draft` and stages rows. Publish commits. Import then inserts live seats. Serialize publish and import finalization on the event row and recheck `draft` under that lock.
- **Delete vs. first booking.** B locks seat S. D locks event E `FOR UPDATE`, sees no orders, and waits to delete S. B inserts its order and waits on the FK’s key-share lock on E. The FK preserves integrity, and this ordering can deadlock. Have booking acquire `FOR KEY SHARE` on E before inventory locks, or insert the private order before those locks. Delete locks E first, then checks for orders in a fresh statement before touching children.

Sample the sales clock after acquiring the allocation locks. If Admin can shorten the window, B can read the old end, Admin can commit a shorter end, and B can then admit using the old end. Freezing it closes that race. **C3. Synchronous creation is sound with guarded finalization.** A and B both call mockpay for attempt P. A saves the intent and returns checkout. The customer pays and the callback commits `paid`. B’s delayed txn2 then blindly writes `awaiting_customer`. In txn2, lock the order first, attach or verify the provider ID, and permit `creating → awaiting_customer` only if the attempt is still `creating` and the order is still eligible. Persist the response for the state you actually found. Bind the request key and hash durably to P in txn1, then resolve that binding before checking eligibility for a new attempt. Otherwise a crash after provider creation followed by expiry can leave a same-key retry unable to find its original operation. An expired `creating` attempt can stop offering checkout, but its merchant ID must remain reconcilable for an in-flight create or late capture. Durable provider dedupe makes the retry converge.

**C4. Assign sequence numbers in the relay, with PostgreSQL committing the mapping first.** Polling unpublished rows fixes the late-ID hole. The remaining failure is R `XADD`s `(seq=42, event=A)`, Redis accepts it, and R dies before PG commits. The next leader sees `last_seq=41` and can assign `42` to B if a lower outbox ID became visible. A client that consumed `42` can silently drop B. Commit the immutable `(event_id, seq, outbox_id)` mapping and watermark in PG first, then forward in sequence order using explicit Redis IDs such as `42-0`. On an ambiguous retry, verify the entry or recover from the durable feed. Read the seat map and watermark in one PG snapshot. Otherwise a map read at seat v5 followed by a watermark read at seq 42 can skip the v6 delta at 42. Absolute, versioned seat updates handle reordering. Use the durable watermark to detect a missing tail even when no later message arrives. **C5. Accept the tradeoff with an explicit temporary result.** Refresh reads zero. Expiry commits a release 1 ms later. A request arrives before the next refresh and gets rejected while a seat is available. That preserves no-oversell, but `insufficient-seats` would overstate what you observed. Use a retryable problem type that says availability is unconfirmed, or coalesce a fresh PG probe before returning `insufficient-seats`. **C6. Materialize the first-page snapshot with a short TTL.** P1 takes publish sequence 100 and pauses. P2 takes 101 and commits. A descending page returns `[101, 99]`. **C7. The strongest Q1 timeline is a captured payment whose callback stalls past expiry.**

1. Mockpay captures for O1 before the deadline. Its callback stalls before locking O1.
2. At the deadline, the sweeper locks O1, expires it, releases S and its active item, and commits. A booking trying S while the sweeper holds it gets `55P03` on the specific-seat path.
3. O2 retries, locks S, holds it, and pays. S is now sold to O2.
4. O1’s callback resumes, locks O1, sees `expired`, and commits the capture record and refund obligation. It performs no seat update.

If O1’s callback gets the lock and samples time before the deadline, it can win instead. The sweeper then skips the locked order or observes `paid`. In the winning callback, require `WHERE status = 'held' AND order_id = :order_id` on the exact active seat IDs, and roll back unless `RETURNING` matches the full set. Under those rules, there is no interleaving where O1’s late callback sells O2’s seat. The active-item unique index protects the claim, while the ownership predicate protects the seat row itself.
