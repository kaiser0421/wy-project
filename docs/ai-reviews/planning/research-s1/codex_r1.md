## P0 · Fix before coding

### 1. Give allocation and release one inventory invariant and one lock order

Define the committed invariant explicitly. An available seat has zero active items. A held or sold seat has exactly one active item belonging to `seats.order_id`, for the same event and zone. Every inventory-owning order has exactly `quantity` active items, and the quota counter equals the sum of active held and sold tickets for that user and event. Add composite FKs for event, zone, and seat membership, retain the partial unique index, and validate distinct requested seat IDs before touching quota. The seat `CHECK` in v1 only verifies whether `order_id` is null. Use `UPDATE … RETURNING` on hold, sale, and release, and abort if the returned seat IDs or item count differ from the order. Build seat events from those returned rows.

Keep the quota row. It serializes **one user’s requests for one event**, which is precisely the contention Q3 requires. The guarded increment is sound when it shares the transaction with allocation and rolls back on every failed allocation, including a short zone selection.

```sql
UPDATE user_event_quota
SET reserved = reserved + :qty
WHERE user_id = :user_id
  AND event_id = :event_id
  AND reserved <= 4 - :qty
RETURNING reserved;
```

The stated deadlock proof is too narrow. `SKIP LOCKED` covers the seat-selection locks. Two sweepers can still claim disjoint orders and then acquire the same quota rows in opposite order. For example, one batch acquires quota A and waits for B while the other holds B and waits for A. Multi-row `UPDATE` gives no contractual lock order. A missing or underflowing quota row must abort release and surface an invariant failure, or the release path can commit with counter drift.

For v2, process **one order per expiry transaction**. Scan candidates without claiming order locks, take the quota row, lock the order, then recheck state and deadline. Multiple workers can discover the same candidate and only one can transition it. Start with this order across booking, cancel, expiry, and payment paths wherever they need those locks: idempotency claim → event gate where applicable → quota → existing order → payment attempt → seats in ascending ID. Keep new rows private until commit. Inventory-neutral operations can skip locks they never need. Design bulk paths separately if one-order transactions prove too slow. Include admin operations and implicit FK locks in the lock graph. [PostgreSQL row locks and deadlocks](https://www.postgresql.org/docs/16/explicit-locking.html)

### 2. Decide the payment deadline after locking, and account for every capture

`now()` is transaction-start time. A callback can begin before expiry, wait on a lock until after expiry, and still accept payment using the earlier timestamp. There is also a branch missing entirely: `pending_payment` with `expires_at <= decision_at`, which is normal when the sweeper is late. If the callback is deduped and acknowledged in that state, the customer can stay charged with no ticket and no refund command.

Take the required locks, then sample `clock_timestamp()` once in a **separate statement**. Define acceptance at that decision point with `decision_at < expires_at`. Use the same boundary on expiry and check it before initiating another attempt. Set the booking TTL near the end of the successful allocation transaction so pool and lock waits do not consume it. [PostgreSQL clock semantics](https://www.postgresql.org/docs/16/functions-datetime.html)

Under the order lock, explicitly handle these cases:

| Verified capture | Atomic local result |
|---|---|
| Pending order, before cutoff, no accepted capture | Record capture, mark order paid, move its exact held seats to sold |
| Pending order at or after cutoff | Expire the order, release its exact items and quota, record capture, enqueue refund |
| Expired or cancelled order | Record capture and enqueue refund |
| Already-paid order | Replay the same capture harmlessly. Record and refund a different capture |

Separate **attempt state**, **provider captures**, and **refund state**. Give the provider capture ID a unique key, and give the order one accepted capture. The existing partial unique index conflates “may start another attempt” with “provider actually charged money.” If attempt A is marked failed, B succeeds, and authoritative reconciliation later discovers a capture on A, the system must be able to record both charges. `succeeded_late` is also absent from the declared enum. Require authoritative provider state or a monotonic provider revision for reordered notifications. A timeout is an unknown outcome, so resolve that attempt before starting another.

I would choose a **strict cutoff plus durable automatic refunds** for this mock provider. A grace period is viable if the seat and quota remain reserved for the whole grace period and there is a clear rule for when an in-flight attempt becomes terminal. A provider timestamp alone cannot justify selling a seat that was already released and reassigned. For paid cancellation, I would revoke the customer’s entitlement immediately and keep the seat and quota reserved until refund confirmation. Confirm the product rule that a completed refund permits resale and restores quota. If the four-ticket limit is lifetime purchase volume, it needs a separate counter or ledger.

### 3. Make payment intent creation, callback application, and refunds recoverable

- **Intent creation.** Commit the local attempt, the idempotent response, and a durable `create_intent` command together. Return `202` with an attempt URL while checkout setup is pending. The worker calls mockpay using the stable merchant payment ID and persists the result. If it dies after the provider creates the intent, retrying the same command must return the same intent. Merely polling `GET /intents/{id}` cannot recover an intent that was never created or whose provider ID was lost. Mockpay must durably persist intents, outcomes, and dedupe keys across restarts.
- **Callback receipt.** Insert the dedupe record, apply the transition, and write any refund or seat events in one transaction. A `2xx` means that transaction committed. A durable inbox with a retrying processor is also valid if acknowledging merely means “durably queued.” The draft’s split receipt/application sequence allows a `kill -9` after receipt to turn every retry into a no-op. Include the event ID in the signed body or signature, validate provider identity, payment ID, currency, and amount, and re-sign each delivery with a fresh timestamp so the five-minute window supports 24-hour retry.
- **Refunds.** Write one durable command per capture with a stable provider refund key. If mockpay refunds and the worker dies before committing the result, retry or query by that key. Keep retryable failures durable and alert on oldest unresolved capture/refund age. Reconcile unknown or nonterminal attempts **after order expiry too**.

The proposed one-second sweep and 30-second reconciliation intervals are polling cadences. Recovery also includes worker restart, queue age, lock waits, and provider availability. In `DESIGN.md`, state when recovery is automatic, give a target under healthy dependencies, and name the unresolved states that page an operator.

### 4. Close the idempotency race and the event-administration race

**Idempotency.** Keep the single transaction for local effects and the recorded outcome. A transaction-scoped advisory try-lock is a reasonable way to return immediate `409 in progress`. Its hash can collide, so use a namespaced, unambiguous encoding and always use the exact `(user_id, key)` row as the identity. A committed matching request replays the status, representation, and stable headers such as `Location`. A committed mismatch returns `422`. While the original transaction is open, `409` is all this design can reliably determine, even if the second request differs. Hash validated semantics, including the concrete resource and normalized seat selection. Authenticate and authorize before replay.

Delete the separate 4xx write transaction. A can roll back and release the advisory lock, B can acquire the key and succeed, and A’s detached error writer can then race with B’s result. Leave contention, availability, quota, and rate-limit failures retryable under the same key. If the product promises replay of a terminal business failure, roll back the business work to a savepoint and persist the outcome while the outer transaction still holds the claim. Define when the 24-hour window starts and what reusing a key after expiry means. If an operation must dedupe beyond that window, give it a durable business identifier.

**Event lifecycle.** A plain event read can observe valid sale dates and prices, then allocate after an admin commits a conflicting edit. An order FK protects event existence and does not serialize sales-window or price changes. Define when admission is decided. One concrete option is a shared transaction advisory gate by event for booking and an exclusive gate for publish, delete, and changes to booking inputs. Take the gate before reading those inputs and enforce it in every writer. Freeze inventory and prices at publication where the product permits. Check the sales window with fresh DB time at the allocation decision. A compliant delete takes the gate before touching children, checks for orders, and keeps the FK as a backstop.

## P1 · Resolve contracts and scaling risks

**Specific seats and zone allocation.** For explicit IDs, use a bounded wait or `NOWAIT`. A contender whose predecessor rolls back should either get the seat after waiting or receive a retryable `seat-busy` response. It should never receive a definitive unavailability result based solely on a skipped lock. Lock the exact IDs in deterministic order, then inspect state.

```sql
SELECT id, zone_id, status
FROM seats
WHERE event_id = :event_id AND id = ANY(:seat_ids)
ORDER BY id
FOR NO KEY UPDATE NOWAIT;
```

Handle `55P03` with rollback and a distinct retryable response. Use `SKIP LOCKED` for interchangeable zone seats and add `id` as a tie-breaker to both the ordering and index. A short result means fewer than `qty` rows could be locked by this attempt. Roll back all changes, then optionally use a fresh PostgreSQL read to distinguish observed shortage from contention. Use a bounded retry with jitter if needed. Remove the Redis zero-availability rejection. It currently makes a stale hint an admission decision, and its staleness can exceed 500 ms if refresh stalls. [PostgreSQL locking clauses](https://www.postgresql.org/docs/16/sql-select.html)

**Outbox ordering.** T1 gets ID 100 and pauses. T2 gets 101, commits, and is published. T1 then commits 100. A consumer advancing a `> 101` cursor misses 100, and an aborted transaction can leave a permanent numerical gap. `SKIP LOCKED` relay replicas introduce further reordering. Seat versions reject stale updates to the same seat and cannot expose a missing update to another seat or a lost tail event. For a simple strict resume contract, assign a per-event sequence by incrementing a transactional counter **after** inventory writes, store the sequence and a batch of seat deltas in the same transaction, and serialize publishing per event. Build the map and watermark from one consistent PostgreSQL snapshot. Retain the durable feed for replay and use a periodic durable watermark so clients can detect a lost tail. On relay death after publishing, duplicate delivery is expected. On Redis loss, replay or resnapshot from durable state. Benchmark the per-event counter because it serializes commits for the hottest event. [PostgreSQL sequence behavior](https://www.postgresql.org/docs/16/functions-sequence.html)

**FK MultiXact and index churn.** Keep the event FK. Concurrent child inserts take compatible key-share locks on the same parent tuple and can create MultiXact overhead even without ordinary lock queues. Shorten booking transactions and measure wait events, WAL, MultiXact activity, and vacuum behavior on the single-event workload. If this is a measured bottleneck, consider physical parent-key sharding with a retained integrity chain. Moving the FK to one other row per event preserves the hotspot. Add `orders(event_id)` for the delete check. Release via `order_items`’ leading `order_id` key and seat PKs, or index the draft’s `seats.order_id` lookup. The availability predicate flips on hold and release, prevents HOT on those updates, and leaves dead entries that scans can encounter. Measure `EXPLAIN (ANALYZE, BUFFERS)`, dead tuples, HOT ratio, and WAL. If churn dominates, compare an explicit available-inventory table or a static seat index with a heap filter. A B-tree lookup cost says little about scanning past dead or locked candidates. [PostgreSQL FK locking](https://www.postgresql.org/message-id/24799.1412951564%40sss.pgh.pa.us), [MultiXacts](https://www.postgresql.org/docs/16/routine-vacuuming.html), [HOT updates](https://www.postgresql.org/docs/16/storage-hot.html)

**§6.2 pagination and import.** Keyset over mutable `sales_start_at` can skip or repeat rows after an edit. Even an immutable key can miss a row whose insert commits behind the cursor. Guarantee the requirement for a defined snapshot by materializing the matching ordered IDs under one snapshot, adding versioned projections if page contents must also remain fixed. Bind the cursor to filters and sort. For import, durably store the input before returning `202`, `COPY` into job-scoped staging with original line numbers, validate set-wise, and use `(event_id, file_sha256)` to return the first job even when a retry names a different mode. A lease needs a fencing token checked in the transaction that finalizes data and job state. Stage outside the event gate, then acquire it and revalidate draft state before finalization. Commit all live rows together for `all_or_nothing`. For `skip_invalid`, make accepted rows, errors, and progress replay-safe. Measure the 100,000-row/60-second target end to end, including validation and finalization.

**Scenario A.** With a ten-minute hold and no cancellations, 10,000 seats cap a 60-second run at 10,000 successful one-seat orders, about **167 successful bookings/sec averaged over the run**. Multi-seat orders lower that ceiling. A 1,500 RPS mixed result can mostly measure rejection. Run the required 3,000 VUs for 60 seconds and report the opening burst, allocation under contention, and exhausted inventory separately. Report committed orders and seats, expected `409`s by problem type, unexpected errors, pool wait, transaction and commit latency, lock waits, and outbox lag. Exercise both hot specific-seat requests and zone allocation, including near exhaustion. The proposed 80 connections and 3–5 ms transaction time are hypotheses. Bound pool acquisition and DB execution, reserve capacity for callbacks and workers, and sweep pool sizes on the actual Compose host.

## P2 · Tighten HTTP and money details

- `If-Match` requires strong comparison. Emit a strong event ETag such as `"v42"` and enforce it with `UPDATE … WHERE id = :id AND version = :expected RETURNING …`. Keep `428` for a missing required precondition and `412` for a mismatch. Bump the version when any field in the protected representation changes. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1), [RFC 6585](https://www.rfc-editor.org/rfc/rfc6585.html#section-3)
- Use `409` for inventory, quota, and order-state conflicts with distinct problem types. Use `422` for invalid selection semantics or a committed key/payload mismatch, `429` for rate limiting, and `503` for temporary capacity failure. Document retry behavior for each problem type. Return `201` with `Location` for completed resource creation, `202` with a status URL for pending checkout or refund work, and `200` with the existing import job on dedupe. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html), [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html)
- The fee formula is correct for nonnegative integer TWD. Use `bigint` or enforce bounds that cover four ticket prices, the intermediate `subtotal * 5`, and the final total. Add immutable price snapshots and a total-arithmetic check.
