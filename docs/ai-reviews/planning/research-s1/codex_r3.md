I’d keep the seat-allocation design. I still disagree with N2’s pagination guarantee, N3’s recovery and purge rules as written, and N6’s overload targets. N7 needs a deterministic race to count as evidence.

### Remaining risks, ranked

1. **Performance collapse — N6.** At opening, ten requests take a process’s ten connections. Same-user retries queue on quota rows while zone allocations repeatedly scan the same locked prefix. Other requests wait for the pool, then return `503` at one second. That can break both p99 < 800 ms and zero 5xx. `SKIP LOCKED` can also return fewer seats while suitable seats are merely locked. Give contention a retryable outcome, measure pool wait separately, and report 503s and paid seats alongside booking latency. Run the payment path if the target is 10,000 **sold** seats. [PostgreSQL locking clauses](https://www.postgresql.org/docs/16/sql-select.html) · [Scenario A](/Users/kaiser/workspace/wy_test/requirement.txt:121)
2. **Stuck payment or refund — N3, N5.** Mockpay creates an intent, the API dies before txn2, and the hold expires. A retry must still resolve the original binding. If a late capture then creates a refund obligation and the refund worker dies after mockpay accepts it, recovery must retry or query by a stable refund key. Keep unresolved bindings out of the 24-hour purge and drive recovery independently of client retries. Sample the DB clock after locking the order. A capture before the deadline whose callback gets the lock after it can be refunded under this policy.
3. **Double charge — N3.** Mockpay accepts intent P1 but its response is lost. A retry with a different client key creates P2 if attempt uniqueness is scoped only to the key. Both checkout sessions can capture. Enforce one chargeable attempt per order, reuse its merchant ID across keys, and require mockpay to capture at most once per intent. Allow replacement only after mockpay confirms the old intent cannot capture. The 10-second threshold makes recovery eligible. It cannot prove the original caller stopped. Check the stored request hash before resuming.
4. **Quota drift — N5 and the refund path.** The sweeper expires O1 and decrements quota. O2 then takes the freed quota. O1’s late capture is refunded, and a generic refund handler decrements again, effectively giving away O2’s quota. Track late-capture refunds separately from quota-bearing orders. Apply quota deltas only on guarded order transitions in the same transaction.
5. **Oversell — N1, N7.** I see no surviving path with the active-item unique index, pre-write seat locks, and exact ownership/count checks on every transition. The critical replay is O1 expires, O2 buys its seat, and O1’s callback arrives. O1 can record the capture and refund obligation while O2 retains the seat. For N7, synchronize the broken variant **server-side after both requests read the seat as available**, then let both write. Assert duplicate committed claims in the broken run. A client barrier alone can miss that race, and a 500 alone proves little. [Q1 test requirement](/Users/kaiser/workspace/wy_test/requirement.txt:130)

### Settled and still disputed

- **N1 settled under `READ COMMITTED`**, with the immediate FK check before seat locks. If booking gets the event lock first, delete waits and its fresh order lookup sees the committed order. If delete wins, booking’s insert fails before it locks seats and the quota update rolls back. Keep any quota rows that deletion touches in the lock graph. [PostgreSQL row locks](https://www.postgresql.org/docs/16/explicit-locking.html) · [Statement snapshots](https://www.postgresql.org/docs/16/transaction-iso.html)
- **N2 still disputed.** Commit-ordered sequence works for the default descending sort while membership stays stable. Page one sees A and B. Before page two, C is deleted or edited out of the filter. C is omitted even though it was visible at page one. A new publish can also enter below a price cursor. A first-page publish watermark excludes new publishes across sorts, but preserving the full first-page result through edits and deletes requires materialized results or historical reads. I’d accept documented live pagination for orders, where the requirement does not mandate stable paging. Concurrent order IDs can commit out of order. [Event pagination requirement](/Users/kaiser/workspace/wy_test/requirement.txt:75)
- **N4 settled** with nonnegative integer subtotals and sufficiently wide arithmetic. **N5’s TTL and clock policy are settled** with the late-capture behavior above. **N7’s mutation approach is settled** once the broken run reliably demonstrates the invariant violation. **N3 and N6 remain open** on the concrete failures above.
