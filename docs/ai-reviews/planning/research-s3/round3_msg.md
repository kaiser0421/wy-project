## D — my counter-proposal instead of materialized snapshot for every query
Materializing every list query (response fields) into Redis per user is heavy and makes the hot "browse events" path stateful. Alternative using PostgreSQL commit-order visibility:
- events has `created_xid xid8 NOT NULL DEFAULT pg_current_xact_id()` (never updated) and soft delete `deleted_xid xid8 NULL` (set via pg_current_xact_id() on delete; hard delete never used for events; events with orders can't be deleted anyway).
- Page 1: server takes `snap = pg_current_snapshot()` (pg_snapshot type, text-serializable), puts it in the HMAC-signed cursor (with filters, sort, subject, issued_at, 10-min expiry).
- Every page: `WHERE pg_visible_in_snapshot(created_xid, :snap) AND (deleted_xid IS NULL OR NOT pg_visible_in_snapshot(deleted_xid, :snap))` + keyset on (sort_key, id).
- This gives exact "membership as of page 1" for inserts and deletes regardless of commit order (late committers with earlier timestamps are invisible to snap since their xid is in xip list or >= xmax).
- Remaining issue: mutable sort keys and mutable filter fields (title, sales_start_at, category, status). Options: (a) default & guaranteed sorts only on immutable keys (created_at, id) and filters only on immutable-or-monotonic fields; mutable sort keys (sales_start_at, title) served by a bounded materialized ID+sort-key snapshot (cap 10k rows, stored in PG unlogged table `list_snapshots` or Redis with TTL) — i.e. your approach only where needed; (b) event_versions history table with valid_from_xid/valid_to_xid and query "as of snap" through pg_visible_in_snapshot — exact for all fields, cost = history table writes on every event update (events are low-write, so cheap).
- I'm leaning to (b): `event_versions` append-only (trigger on update writes old version with valid_to_xid = current xid). Page query: rows from events whose current version visible in snap, UNION versions whose [valid_from_xid visible, valid_to_xid not visible]. Hmm — that's complex SQL. Maybe (a) is cleaner.
Questions: Is xid8/pg_visible_in_snapshot approach correct (wraparound? replicas? snapshot size with many concurrent txns at peak — xip list could be long during 3000 VU booking load, making the cursor large)? Which of (a)/(b)/your materialization do you pick for this implementation?
