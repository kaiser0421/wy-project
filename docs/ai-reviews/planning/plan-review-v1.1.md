## 2. Remaining inconsistencies and exact fixes

1. **Release and capture handling.** In §5.4, split the diagram into accepted capture, duplicate capture replay, expired-but-still-pending capture, and money-only refund. The expired-but-still-pending branch must call `release_order()` in the same transaction. In §5.1, remove duplicate capture from the list that creates refunds. In §5.6, lock each candidate order and recheck the deadline with `app_now()` before release, as required by that section’s post-lock clock rule. [§5.1](/Users/kaiser/workspace/wy_test/PLAN.md:250), [§5.4](/Users/kaiser/workspace/wy_test/PLAN.md:337), [§5.6](/Users/kaiser/workspace/wy_test/PLAN.md:360)

2. **Payment recovery has no single transaction contract.** §5.3 says only successes are stored, then requires payment terminal responses to be persisted. §5.4’s diagram never writes the idempotency record. Define txn1 to persist the key, hash, and attempt link together and txn2 to persist the attempt result and exact replayable response together. Specify the failure response and how API and reconciler finalize the same attempt. Recheck capture identity under the order lock before deciding its disposition, so two callback event IDs carrying the same capture cannot both take the new-capture branch. Persist provider-cancellation work when cancelling a pending order. State the W3/W5 timing assumptions for queue depth and provider availability. [§4](/Users/kaiser/workspace/wy_test/PLAN.md:175), [§§5.3–5.4](/Users/kaiser/workspace/wy_test/PLAN.md:307), [§5.7 W3–W6](/Users/kaiser/workspace/wy_test/PLAN.md:374)

3. **Relay delivery can still skip a sequence.** §6.2 shows assignment followed by append and checkpoint, while §5.7 gives recovery rules only for restart. On every delivery pass, retry exactly `last_delivered_seq + 1` and advance only after an acknowledged append or exact ID and payload verification. Define the rebuild path when verification fails, including when the new generation becomes visible. For each subscriber, capture a replay cutoff and join live delivery at the next contiguous sequence. Restore the PostgreSQL replay step in §6.1’s slow-client ladder and standardize the snapshot response on `gen`, `last_assigned_seq`, and seat versions in §11 and T4.2. [§5.7 W2/W8](/Users/kaiser/workspace/wy_test/PLAN.md:373), [§§6.1–6.4](/Users/kaiser/workspace/wy_test/PLAN.md:389), [§11](/Users/kaiser/workspace/wy_test/PLAN.md:615), [§21.2 T4.1–T4.5](/Users/kaiser/workspace/wy_test/PLAN.md:908)

4. **Layout refresh has a new race.** §6.4 introduces `layout_ver`, but §4 does not store it and §6.1 permits a one-second snapshot cache. A client can receive `layout_changed` and fetch the old layout from another replica. Persist the layout version in the finalize transaction, include it in snapshots and layout events, and require a refresh to return at least the announced version before applying deltas indexed against that layout. [§4](/Users/kaiser/workspace/wy_test/PLAN.md:155), [§6.1](/Users/kaiser/workspace/wy_test/PLAN.md:397), [§6.4](/Users/kaiser/workspace/wy_test/PLAN.md:445)

Amend the diagram to put durable file placement, including the directory sync after rename, before the `queued` commit. Resolve identical-file replay before rejecting a new import on draft or active-job grounds, after checking caller access. [§5.6](/Users/kaiser/workspace/wy_test/PLAN.md:365), [§7.5](/Users/kaiser/workspace/wy_test/PLAN.md:485), [§8](/Users/kaiser/workspace/wy_test/PLAN.md:490), [§8 finalize](/Users/kaiser/workspace/wy_test/PLAN.md:514)
