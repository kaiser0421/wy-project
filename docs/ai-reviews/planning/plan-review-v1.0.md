**Verdict: revise before coding.** The plan names nearly every required deliverable, but its seat-stream snapshot can move the UI backward, its payment recovery can create a second chargeable intent, and its pagination watermark cannot preserve a filtered result set. Those are design defects that acceptance testing alone will not fix.

## 2. Correctness defects

- **Relay sequence and seat version (§§4, 6.1–6.4, 19).** The same-seat argument works if every writer locks and updates that seat **before** allocating its outbox ID, IDs increase across writers, and one relay sequences committed unassigned rows in ID order. Row locks alone establish none of the outbox-ID conditions. Different seats can appear out of commit order, and a multi-seat transaction can span relay batches. A coalescer must retain the highest version per seat and advertise only the contiguous sequence range it consumed.
- **Snapshot and `seq` (§§6.1–6.3).** Suppose the relay head is 10 while a seat’s `held/v1` and then `available/v2` have both committed. The snapshot returns `available` at 10. Replaying `held/v1` at 11 moves the bitmap backward because it carries no baseline version. `REPEATABLE READ` makes the reads consistent with one DB snapshot. It cannot make the relay catch up to the seat writes. Also, `pg_head == applied` during a relay stall with unassigned rows, so healthy heartbeat frames can leave a stale UI looking current. [PostgreSQL transaction isolation](https://www.postgresql.org/docs/16/transaction-iso.html)
- **Relay crash recovery (§§4, 5.7 W8, 6.1–6.4).** Assigning `published_seq` before `XADD` removes the row from the only specified polling predicate. A crash in between can strand it. After `XADD` succeeds but its acknowledgement is lost, retrying the same explicit ID returns an error. The plan conflates assignment, delivery and Redis tail and leaves generation out of the SSE resume ID. [Redis XADD](https://redis.io/docs/latest/commands/xadd/)
- **Watermark pagination (§§5.6, 11, 20).** A published event below the watermark can change category or search text between pages, causing an omission or a new match. Draft publication and deletion also change membership. A nonunique sort key such as price needs an ID tie-breaker. If the first page and watermark are read in separate `READ COMMITTED` statements, a commit between them can enter the watermark while missing the first page. `published_seq` alone cannot represent owner/Admin draft listings. [PostgreSQL transaction isolation](https://www.postgresql.org/docs/16/transaction-iso.html)
- **Idempotency and payment (§§4, 5.2–5.4, 5.7).** During an uncommitted booking, the try-lock loser cannot compare the original hash, so a different payload can receive 409 before it can receive 422. For payment, a persisted `in_progress` row has no specified ownership, takeover or terminal failure response. An ambiguous provider timeout followed by `abandoned` can free the unique slot while the original intent is still chargeable. A callback with a new event ID and an already accepted capture ID must replay the stored capture disposition before it considers refunding a paid order. W3’s ≤30s recovery also conflicts with polling an `awaiting_customer` intent only after expiry plus two minutes. [PostgreSQL transaction isolation](https://www.postgresql.org/docs/16/transaction-iso.html)
- **Quota and release (§§4, 5.1–5.6).** §5.1 releases an expired pending hold on a late callback. §5.4’s late branch leaves quota unchanged. For a `pending_payment` order past deadline, either leaving the hold pending contradicts the state machine or releasing it without decrementing quota creates drift. An already released order and an extra capture on a paid order take a money-only refund path. A paid cancellation retains the claim and quota until its accepted capture is refunded. Decide explicitly whether a completed refund restores eligibility under the four-ticket cap.
- **SQL locking and allocation (§§4, 5.2, 5.6, 11, 14).** `SKIP LOCKED` can return fewer than requested while eligible seats are locked by a transaction that later rolls back. One-shot requests cannot guarantee 150 successes. The lock-order proof also omits FK, table and batch lock waits. If expiry handles multiple orders in one transaction, sorting quota locks per order still permits two workers to acquire Q1→Q2 and Q2→Q1. Specify whole-batch ordering or one order per release transaction. Separately, checking an ETag in application code before an unconditional `UPDATE` still permits a lost edit. [PostgreSQL SELECT locking clauses](https://www.postgresql.org/docs/16/sql-select.html)
- **Import vs. publish (§§5.6, 7.3, 7.5, 8).** Publish can see no active job and commit while admission, which has no specified event lock or in-transaction draft recheck, queues one. Finalize’s draft check then rejects an upload already acknowledged with 202. §6.4 also assumes drafts have no subscribers, while §7.3 permits them for owners and Admins. A stale worker’s final `UPDATE … WHERE fence = …` protects prior inserts only if a zero-row result aborts the entire transaction.
- **Revocation cost and check-to-use race (§§5.7 W9, 6.2, 7.1, 18–19).** At 2,000 distinct sessions, 100 ms revalidation means approximately **20,000 session-ID checks/sec** and up to 30 batch queries/sec across three replicas, assuming one batch per replica per tick. Multiple per-event loops could exceed that query count. A revocation can commit after a tick validates but before it writes, and a frame already buffered can still arrive. Pub/Sub can be lost. A tick-only check also leaves quiet connections open unless it runs independently of deltas. Define when HTTP authorization takes effect, and give SSE a measurable closure deadline and pool budget.
- **Excel on a single-worker API (§§2.1–2.2, 9, 11, 13.1, 18).** Direct XLSX writes and ZIP finalization inside an async handler can stall booking and SSE on that replica. `constant_memory` addresses worksheet buffering. The semaphore limits export concurrency. Neither isolates blocking work or bounds disk, page cache, long snapshots, or abandoned files. §2 promises an export worker, while §9 makes the API the execution path. [FastAPI execution model](https://fastapi.tiangolo.com/async/)
- **Telemetry (§§10.1–10.5, 13.3).** Commit-before-ACK deduplicates samples that reach the collector. A producer crash or Redis loss can erase samples, including the last one with no later sequence gap. Catch-up can bunch multiple flushes into the same receive-time second, spike RPS, and double-count connection gauges if summed. Receive time minus producer wall time includes queue delay, so the skew alert can misdiagnose collector backlog. The edge-to-k6 reconciliation also needs matching route, time and stream-exclusion rules.

## 3. Quality and delivery risk

- **Pull the hard acceptance tests forward (§§13–16).** A clean Compose run, a real 100k import, a 500k API export under the memory cap, and 2,000 SSE connections can invalidate foundational choices. Make a runnable vertical slice and resource smoke tests before UI polish or M9.
- **Cut scope around the required paths (§§2–3, 10.5, 12, 13, 15–16).** Start with one relay, a basic seat map and the required charts, a few actionable alerts, and the exact A/B scripts. Defer relay failover complexity, synthetic checkout, advanced Canvas layers, the extended load sweep and milestone PR/tag ceremony until required checks pass.
- **Settle implementation contracts (§§4–5, 7–9, 11, 20).** Write complete state transition tables and constraints for event/zone/seat ownership, quota, cancellation and captured money. Define report revenue by state and refund treatment, import retry eligibility and file cleanup, cursor lifetime, and nested-resource authorization. Use a documented default hold TTL.
- **Make verification falsifiable (§§13.3, 14, 16–17).** Separate expected contention from HTTP errors and business failure. Use barriers for races, run the same oversell assertion against a broken build, keep mutation hooks out of the production image, and compare DB and client hashes only after the system drains to a defined checkpoint.
